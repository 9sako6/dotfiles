# カード設計規約

## 1. 想起の単位

- 1カードにつき、思い出す対象を一つにする。表面を読んで5〜15秒程度で答えられる粒度を目安とする。
- 列挙を丸ごと問わない。一項目ずつ分けるか、既知の項目を表面に与えて残り一つを問う。
- 「どこで誰が運用する？」のような二重質問を避ける。疑問が二つあるなら分ける。
- 一つのノートから複数カードを作る形式は、復習量が増えることを確認してから使う。
- Basic、逆カード、Clozeのどれかへ固定しない。既存ノートタイプがなければ、一つの想起対象を問う一方向カードから始める。

## 2. 問題文

対象、具体的な条件、答えの種類を表面に書く。`これは？` や `何という？` だけで終わらせない。表面には、答えを一意に特定するための必要十分な文脈だけを置く。情報不足で複数の答えが成立する問いにせず、答えそのものを示唆する説明や不要なヒントも足さない。

デッキ名、タグ、Goal名などの管理メタデータは、問いを成立させるための文脈として本当に必要な場合を除き、表面に表示しない。分類情報が意図しない想起の手掛かりになるのを避ける。

基本形は次のとおり。

```text
識別力の高い具体的な定義 + 答えの種類 + を何と呼ぶ？
```

例:

- `1日の約定値を取引成立順に並べた記録を何と呼ぶ？`
- `障害時に書き込みを引き継ぐ待機系サーバーを何と呼ぶ？`
- `この症状が出たとき、最初に確認するログはどれ？`

略称、正式名、別名、表記を答えさせる場合は、求める回答形式も表面に書く。`どこ？` は実際の場所を答える場合だけに使う。転送先、処理主体、所有者を問う場合は、`サービス`、`コンポーネント`、`プロセス` など、答えの種類を明示する。

公式説明やコード上の事実から離れすぎないようにする。短くするために近縁概念との違いを消さず、由来や具体例が記憶の手掛かりになる場合は残す。

### 1枚で完結させる

カードは文脈を持たない。表面だけで、何の話か、どの組織やシステムの話か、誰が決めたことかが分かるようにする。`この`、`その`、`上の` で他のカードや前後の問いを指さない。デッキやタグで分かるはずの文脈も、必要なら本文に書く。図が同じカードに表示される場合は、`図は` で始めてよい。

### 出どころを書く

そのルールや事実が誰の決まりかを、表面の文に入れる。組織が独自に決めたことを一般的な決まりと思い込んだり、ツールの仕様を組織の都合と取り違えたりしないようにするため。

| 出どころ | 書き方の例 |
|---|---|
| 組織が独自に決めた規約・方針 | `〇〇が独自に決めた△△の規約では、……。業界で一般的な決まりではない。` |
| 組織のシステムの構成・設定 | `〇〇では独自に、……と設定している` |
| 組織の業務ルール | `〇〇の業務ルールでは、……` |
| ツールや製品の仕様 | `Git（バージョン管理ツール・OSS）の仕様では、……` |
| 業界の慣行・一般的な技術用語 | `業界で一般的な慣行として、……` |
| 標準規格 | `HTTPの規格（RFC 9110）では、……` |

独自の規約は、一般的な決まりではないことを一文で書いて強める。出どころが混ざるときは両方書く（例: 2系統あること自体はライブラリの仕様で、混ぜて使うのを禁じているのは組織の規約）。出どころは根拠で確かめ、判断できなければ書かない。

### 名前が何かを書く

製品、ツール、ライブラリ、組織内のシステムの名前は、表面で初めて出るところに、それが何かを括弧で添える（例: `ADOdb（PHPのDBライブラリ・OSS）`）。組織内のシステムの説明は、全カードで同じ言い方にそろえる。答えそのものや、答えを強く示す説明は表面に書かない。

### 答えの種類が決まらない問いにしない

`どんな状態？`、`どういう扱い？`、`何が起きる？`、`役割は？`、`一番の利点は？` は、条件・意味・結果のどれを答えるかが決まらず、正解が複数になる。条件、値、理由、名前のどれを問うのかを決めて書く。

- 悪い例: `フラグが true のとき、レコードはどんな状態？`
- 良い例: `フラグが true になる条件は何？` と `フラグが false のとき、非公開か掲載終了かを見分ける項目はどれ？` の2枚に分ける

`〜は正しい？` に `正しくない` と一語で答えさせる問いも、何が正しいのかを問う形にする。

### 目的を書く

計測、比較、繰り返し、確認などの操作を問うカードでは、何を判断するための操作かを表面に書く。操作だけでは複数の目的が考えられ、正解の範囲が定まらない。

- 悪い例: `CSV処理を繰り返したとき、各回のGC後の推移で何を確認する？`
- 良い例: `一時的なピークと処理後まで残る増加を見分けるには、各回のGC後の値で何を確認する？`

目的を足した結果、一枚で目的と手順の二つを答えさせない。目的は表面で与え、短答では判断点だけを答えさせる。

### 疑問詞と短答を揃える

疑問詞と文末が要求する答えの種類を先に決め、その種類の短答を書く。

| 表面が求めるもの | 短答の形 |
|---|---|
| `どこに置く？` | 場所や位置 |
| `何が変わる？` | 変わる対象 |
| `どう変わる？` | 変化の方向や結果 |
| `何を確認する？` | 確認対象、または `〜か` で終わる判断点 |
| `どの値／項目／キー／識別子？` | 同じ種類の名称 |
| `できる？` | `できる／できない` |
| `なぜ？` | 理由 |

質問と短答で、値、識別子、式などの種類をずらさない。

## 3. 答えと補足

答えを先に置き、採点時に探さなくてよい形にする。説明、例外、由来、正式名称は、既存ノートタイプに適切な補足や参考フィールドがあればそこへ分ける。

裏面の情報は `短答 → 補足 → 出典` の順に置く。まず正誤判定に必要な短答を一目で読める位置へ出し、その後に理由、境界条件、例、一次資料を続ける。補足や出典の中へ正答を埋め込まない。

表面の直後に短答を続けて読み、日本語の応答として成立するか確認する。意味は近くても種類が違う組み合わせを通さない。

略語は初出時に正式名称を確認できるようにする。ただし、その学習対象で既知と確認した汎用語まで毎回展開しない。

短答が名前で、その種類が表面から分からないときは、短答の直後に括弧で種類を添える（例: `imgproxy（製品名・OSS）`、`FireLens（AWSの機能名）`、`Kappa（組織内の通称）`）。明らかなものや一般用語には付けない。

複数の条件や項目が絡む概念を、一語の短答で言い切らない。補足に例外を書いても短答が誤った理解を与えるなら、カードを分ける。

答えが長い場合は、複数の事実を一度に採点しようとしていないか確認する。長さ自体が必要な定型文やコードなら例外として扱う。

## 4. 前提知識と順序

理解できていない内容を、そのまま暗記対象にしない。まず意味や他の概念との関係を理解し、説明できる粒度にしてからカード化する。本編で新しい語彙を使う前に、その語彙を学習者が説明できるか確認し、説明できなければ手前の基礎カードを追加する。

カード案とAnkiへの追加順は、前提から依存先へ進む順にする。この順序は新しい知識の導入順であり、通常の復習順を固定するためには使わない。復習順はAnkiのスケジューラに任せる。

技術領域では次の並びが使いやすい。これは例であり、対象に合わせて層を増減する。

1. 製品に依存しない一般概念
2. 基盤や製品での実装名
3. 対象システムの実際の構成

個別事実が揃ったら、状況から知識を引き出すカードを加える。

- `この症状なら最初に何を疑う？`
- `この変更で先に確認する境界はどこ？`
- `なぜこの構成を選んでいる？`

名前当てだけで埋めず、理由、判断、障害対応を到達目標に合わせて混ぜる。

## 5. 重複と近縁概念

新しいカードを作る前に既存カードを確認する。

- 同じ事実を同じ想起方向で問うカードを重複させない。
- 表記が同じでも意味が違う概念は別カードにし、表面で区別できる条件を書く。
- 同義語、略語、表記違いは、通常使う名称の一枚へまとめる。別名を独立して思い出す必要がある場合だけ分ける。
- 上位概念と下位概念、状態と手続きなど、意味差があるものを同義語として統合しない。
- 近縁カードは共通点だけでなく、そのカードだけを正解にする差異を表面に入れる。
- 強く干渉して互いを取り違えやすい近縁概念は、同じ投入単位へ無理に詰め込まない。必要なら片方を先に学び、もう片方を後の候補へ回す。

既出の事実を、応用やシナリオとして別の状況から問うことは重複とみなさない。

## 6. 根拠と変化

カードの事実は一次資料で確認する。コード、設定、仕様書、公式リファレンスを優先し、解説記事だけを根拠にしない。

台数、容量、料金、バージョンなど変わりやすい値は原則として避ける。値そのものの暗記が到達目標に必要なら、更新元を明確にしてから入れる。

既存ノートタイプに参考フィールドがあれば、復習時にも役立つ一次資料をそこへ残す。専用フィールドを勝手に増やさない。

ツールや製品の仕様を問うカードは、確かめた版を参考の末尾に書く（例: `確認した版：Git 2.56.0（2026-10-23）`）。版番号の無いクラウドサービスは確認日を書く（例: `確認日：2026-10-23（AWS公式ドキュメント）`）。版を暗記させるためではなく、知識が古くなったかを後で見分けるため。

資料自身が「未確認」「推測」と断っている名称や略語の展開を、正式名称として写さない。組織の独自用語は、展開せずそのまま使う。資料と実装が食い違うときは、実装を根拠にカードを書き、食い違いを人間に報告する。

## 7. レビュー

追加前に次を確認する。

- [ ] 各カードの事実を一次資料で確認した
- [ ] 暗記する前に、内容の意味と関係を理解できている
- [ ] 思い出す対象が一つである
- [ ] 表面だけで対象と答えの種類が分かる
- [ ] 表面だけで、何の話か、どの組織やシステムの話か、誰の決まりかが分かる
- [ ] 初出の製品・ツール・組織内のシステムに、それが何かを添えている
- [ ] 種類が分かりにくい名前の短答に、名前の種類を添えている
- [ ] ツールや製品の仕様のカードに、確かめた版か確認日がある
- [ ] 表面の文脈が答えを一意にするために必要十分で、不要なヒントを含まない
- [ ] デッキ名、タグ、Goal名などの管理メタデータが不要な想起の手掛かりになっていない
- [ ] 操作を問うカードでは、その操作で何を判断するのかが表面にある
- [ ] 疑問詞と文末が要求する答えの種類に短答が一致する
- [ ] 表面の直後に短答を続けて読んでも、自然な応答になる
- [ ] 裏面が短答、補足、出典の順で、正答をすぐ採点できる
- [ ] 近縁概念も正解にならない
- [ ] 答えが採点しやすい位置にある
- [ ] 未学習の前提語彙を放置していない
- [ ] 新しいカードが前提から依存先への順に並んでいる
- [ ] 強く干渉する近縁概念を同時に詰め込みすぎていない
- [ ] 同じ事実の既存カードと重複していない

本文を通読し、同一カード内で疑問文同士が衝突していないか、また括弧による補足がなければ成立しない問いが含まれていないかを確認する。

複数回答の疑いとして、少なくとも `それぞれ`、`いくつ`、`何と何`、`すべて`、`全て`、`の順で`、`どんな`、`どういう`、`何が起きる` を確認する。ヒットは機械置換せず、一枚ごとに判断する。
