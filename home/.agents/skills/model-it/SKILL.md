# Goal

ユーザーの脳内に、操作可能なモデルを構築すること。
ユーザーは、文章そのものや正式名称を暗記するよりも、概念間の関係や全体構造を内部モデルとして保持することを重視する。
思考そのものは言語の形をしておらず、言語から構造への変換には時間がかかる。
情報を意味のあるまとまりに分け、関係や因果を捉えられるようにすることで扱いやすくなる。
そのため、本スキルは原文を忠実に記憶させるのではなく、情報を圧縮可能な構造へ変換し、ユーザー自身の内部モデル形成を支援する。

# Input

ユーザーが理解したい対象。

# Modeling

単に文章を要約するのではなく、背後にあるモデルを再構築する。
理解に適した構造にするため、必要に応じて原文の分類から外れて組み替えてよい。
また、知識獲得がスムーズに進むよう、原文の構成順から外れて再構成してよい。
まずは粗いモデルから作成し、徐々に詳細化して完成度の高いモデルへと発展させる。

- 処理や因果の流れがある対象では、具体的な入力例を1つ選び、その値が各段階でどう変わるかを追う図をまず検討する。条件の組み合わせや分類は、具体例の図だけでは説明が足りないときに足す。
- 処理の流れは、読む順を実行順にそろえる。序数・指示語・略称は、指す対象を先に示してから使う。「1回目」なら、何の処理を数えているかを先に説明する。
- 比較は両辺を、変化は前後を具体的な値で示す。たとえば、金額の単位を円と示したうえで、割引は `3000 - 500 = 2500`、送料無料の判定は `2500 >= 3000 → false` と書く。どの段階の値かも示し、「そのもの」「同じ」だけで済ませない。
- 値・リテラル・式は説明文と別のノードに置き、形や色で区別する。値のノードにはコード表記だけを入れ、出力先で使えるなら等幅フォントにする。見慣れない記号を使う場合は凡例を添える。

# Output

モデルを作る前に、出力先（端末・PR本文・ドキュメントなど）と希望する図の数を、依頼や会話の文脈から確認する。不明で選択に影響する場合はユーザーに聞く。
出力先に合わせて、Mermaidの図の数と書き方を決める。PRやIssueに貼る完成図は1つを基本にする。複数の観点の図を出すのは、どれを載せるか選んでもらう段階に限る。図の数が指定されている場合はその指定に従う。
学習やドキュメントでは、理解に必要な場合に複数の観点を可視化してよい。

GitHubに貼る場合は、ラベルを短くし、端末の下書きだけで判断せず、貼り付け先で折り返しや改行の描画を確認する。改行を値として見せたいときは、ラベル内の改行や `\n` に頼らず、`A↵B` と「`↵` は値に含まれる改行」のような凡例で表す。
対応する構文は[GitHubのMermaid案内](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/creating-diagrams#creating-mermaid-diagrams)で確認する。

`/copy` を使えるように、Markdownのみで出力する。
