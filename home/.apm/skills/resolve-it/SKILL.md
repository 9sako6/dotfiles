---
name: resolve-it
description: >
  実現したいことと守るべき条件をもとに、実現方法の選択肢と依存関係を一問ずつ解き、
  実装できる具体度まで設計を確定する。
  Use when user wants to turn a request, issue, spec, bug, or existing design into an implementation plan, or mentions "resolve it".
---

このスキルの目的は、実現したいことと守るべき条件を変えずに、それをどう実現するかを決めることにある。Issue、仕様、要望、不具合、既存の設計案、会話で決まった方針など、実現したいことを判断できる情報があれば始められる。

まず、入力から次を把握する。

- 何を実現したいか
- 何を守る必要があるか
- 現在どうなっているか

情報に不足があっても、すぐに質問してはならない。既存実装や資料を調べれば分かることは自分で確認し、実装の判断に必要な分だけ推論または質問する。何を実現したいか自体が曖昧で実装案を選べない場合は、その判断に必要な情報だけを掘り下げる。

実装都合だけで、入力から分かる目的や守るべき条件を変えてはならない。実現不能、安全上の問題、重大なコストが判明したときだけ、何が衝突しているかを明示したうえで判断を戻す。

まず既存の仕組み、制約、慣習、現在の実装を確認する。標準機能や既存の抽象で足りるなら、それを優先する。新しい概念、状態、設定、コマンド、独自レイヤーは、必要性を説明できる場合のみ追加する。

実現方法について複数の見立てを持ち、回答ごとに見直す。依存する判断は上流から解き、次は、その答えによって重要な実装案の違いが明確になり、後の判断を大きく減らせる一問を選ぶ。

質問は一度に一つだけとする。毎回、推奨案と理由を短く添える。既知の情報や、既存実装を調べれば分かることは聞かない。答えが実装を変えない質問もしない。安全に推論できることは自分で決め、その判断を説明する。

機能一覧を増やす方向へ話を広げてはならない。常に、実現したいことと守るべき条件に必要かを基準とし、簡単に実装できることと実装すべきことを分ける。

特に、次の境界が曖昧なまま実装へ進んではならない。ただし項目を順番に質問するのではなく、必要なものだけを判断する。

- source of truth: 情報を管理・参照する際に、何を基準とし、どの情報に従うか
- ownership: どの層、モジュール、サービスが責務を持つか
- state: 何を保存し、何を導出するか
- boundary: 標準機能と独自実装の境界をどこに置くか
- failure: 途中失敗で何が残り、どう復旧するか
- observability: ユーザーや運用者が何が起きたか確認できるか
- compatibility: 既存の操作、データ、標準的な逃げ道をどう守るか
- migration: 現在の状態から安全に移行できるか

選択肢を比較するときは、実装量だけでなく、理解しやすさ、変更しやすさ、失敗時の挙動、標準からの距離、将来削除できるかを考慮する。不要な汎用化や、まだ存在しない将来要件のための複雑化は避ける。

ユーザーの主体性、単純さ、安全性、透明性など、その実現方法によって損なわれる重要な性質がないかを考える。原則同士や実装上の制約が衝突した場合は、実現したいことと守るべき条件に立ち返って優先する。

次の質問をしても実装方針や重要な境界が変わらないなら止める。細部をすべて人間に決めさせてはならない。残りを実装者が安全に決められるところまで解ければ十分である。

最後に、実装へ渡せる短いブリーフをまとめる。少なくとも、採用する方針、守る不変条件、どの情報に従うかの判断と責務の境界、主要な処理の流れ、失敗時の扱い、移行と検証方法を残す。重要な代替案を捨てた理由がある場合のみ、それも残す。コードや具体的なパッチの作成は、ユーザーが実装まで求めた場合に進める。
